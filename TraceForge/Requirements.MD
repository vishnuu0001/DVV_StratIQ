# TraceForge — Build Specification Prompt

> **Instructions to the coding agent:** This is a complete build specification. Implement it end-to-end. Do not ask clarifying questions unless a requirement is genuinely contradictory. Where a choice is left open, pick the option marked **[DEFAULT]**. Every artifact the system emits must be traceable to a source citation — this is the single non-negotiable design constraint.
>
> **Deployment constraint — read this first, it changes design decisions throughout:** This application is hosted on a **Windows Server 2022 Azure VM running IIS**. **Containers are not available.** Do not use Docker, docker-compose, Kubernetes, or any container-dependent pattern (including containerised sandboxes, sidecars, or `testcontainers`). Every runtime component must run as a native Windows process, a Windows Service, or an IIS application. Every dependency must have a working Windows wheel or a Windows-native binary. See **§13 Azure VM / IIS Deployment Architecture** — it is normative, not advisory.

## 1. Mission

Build **TraceForge**, an AI-assisted SDLC artifact factory that ingests heterogeneous enterprise source material (ServiceNow data, AS-IS documents, SOWs, process maps, legacy code) and produces a **traceable chain of deliverables**:

```
Source Corpus → RAG Index → Requirements (REQ) → BRD → Test Cases (TC) → Test Scripts (TS) → RTM + Evidence Pack
```

Every stage is generated by an LLM agent, **grounded in cited source chunks**, **gated by a human approver**, and **linked by a persistent traceability spine**.

The product is NOT a chatbot. It is a **workbench**: agents draft, humans adjudicate, the system remembers.

### 1.1 Design Principles (enforce these in code, not just docs)

| # | Principle | Enforcement mechanism |
|---|---|---|
| P1 | **No ungrounded artifact** | Every `Requirement` MUST have ≥1 `SourceCitation` row. DB constraint + API validator rejects otherwise. |
| P2 | **Traceability spine is mandatory** | `REQ-ID → TC-ID → TS-ID` foreign keys are `NOT NULL`. Orphan detection job runs on every stage transition. |
| P3 | **Humans own the gates** | No downstream agent may execute until the upstream stage is `APPROVED`. Enforced in the orchestrator state machine, not the UI. |
| P4 | **Change propagates as "suspect"** | Editing an approved Requirement marks all downstream TC/TS as `SUSPECT`, never silently deletes them. |
| P5 | **Deterministic, stable IDs** | IDs are assigned once and never reused or renumbered, even after deletion. |
| P6 | **The LLM is swappable** | All model calls go through a single `LLMProvider` interface. Anthropic / Azure OpenAI / self-hosted vLLM must all work by config change only (air-gapped deployments are a hard requirement). |
| P7 | **Everything is audited** | Every state transition, edit, approval, and LLM call writes an immutable `AuditEvent`. |

## 4. Ingestion Layer

### 4.1 ServiceNow Connector

Implement `connectors/servicenow.py` using the **Table API** (`/api/now/table/{table}`) with basic auth or OAuth2 client-credentials.

Supported tables (configurable per project):

| Table | doc_class | Purpose |
|---|---|---|
| `incident` | `INCIDENT_DATA` | Volume/pattern mining → NFRs, error-handling requirements, negative test cases |
| `sc_req_item` / `sc_task` | `AS_IS_DOC` | Existing service catalog behaviours |
| `change_request` | `AS_IS_DOC` | Known change patterns, CAB constraints |
| `kb_knowledge` | `KB_ARTICLE` | Documented AS-IS process |
| `cmdb_ci` | `OTHER` | System/CI names → glossary + system_name resolution for EARS |
| `sys_attachment` | (delegate to file parser) | Attached SOWs, process maps |

**Critical:** incident data is *tabular*, not prose. Do NOT naively embed 25,000 incident rows as chunks — the RAG index will be useless.

Instead run a **pre-aggregation pass**:
1. Pull incidents with a configurable window (default 12 months) and field set (`number, short_description, description, category, subcategory, u_application, cmdb_ci, priority, resolution_notes, opened_at, closed_at`).
2. Cluster by `(category, subcategory, u_application)` + semantic clustering of `short_description` (HDBSCAN over embeddings).
3. Emit **one synthesized chunk per cluster** of the form:

```
INCIDENT PATTERN: {cluster_label}
Application: {app}  |  Category: {cat}/{subcat}
Volume: {n} incidents over {window} ({pct}% of total)
Median resolution: {hours}h  |  P1/P2 count: {n}
Representative examples:
  - INC0012345: {short_description}
  - INC0012876: {short_description}
Common resolution actions: {top-5 extracted verbs/objects from resolution_notes}
```

4. The locator for these chunks is `{ table: "incident", cluster_id, incident_numbers: [...] }` — so a Requirement citing this chunk can drill down to the actual INC numbers in the UI. **This is the feature that makes the demo land.**

Raw incident rows are still stored (in a `servicenow_incident` staging table) so drill-down works, but only the synthesized cluster chunks go into the vector index.

### 4.2 File Parsers

| Type | Parser | Locator granularity |
|---|---|---|
| `.docx` | python-docx → walk paragraphs + tables, retain heading hierarchy | page (approx), section heading, char offsets |
| `.pdf` | pymupdf → text + layout; OCR fallback (tesseract) if text layer < 100 chars/page | page, block bbox |
| `.xlsx` | openpyxl → one chunk per logical table region, header-aware | sheet, row range |
| `.pptx` | python-pptx → one chunk per slide (title + body + notes) | slide number |
| `.vsdx` / `.bpmn` | Parse shapes + connectors → emit a **textualised process flow** ("Step 1 [Task]: Capture Order → Step 2 [Gateway]: Credit Check? → …") | shape id |
| Process map images | Vision model pass (`claude-sonnet-4-6` with image input) → textualised flow, flagged `low_confidence` | image region |
| Legacy code | tree-sitter → chunk per function/class/module; extract signatures, comments, SQL, business rules from conditionals | file path, line range |

### 4.3 Chunking & Indexing

- **Structure-aware chunking**, not fixed-size. Split on heading boundaries; target 400–800 tokens; overlap 80 tokens; never split a table row.
- Embed with `voyage-3` or Azure `text-embedding-3-large` **[DEFAULT: configurable via `EMBEDDING_PROVIDER`]**. Air-gapped fallback: `bge-large-en-v1.5` on the local GPU.
- **Hybrid retrieval**: pgvector cosine similarity + Postgres `ts_rank_cd` BM25, fused with **Reciprocal Rank Fusion** (k=60). Vector-only retrieval will miss exact identifiers ("INC0012345", "ZORDER_CREATE") — this is a known failure mode; do not skip BM25.
- Rerank top-50 → top-12 with a cross-encoder (`bge-reranker-v2-m3`) before passing to the agent.

## 5. The Agents

All agents share this contract:

```python
class AgentResult(BaseModel):
    items: list[BaseModel]              # schema-validated output
    citations: dict[str, list[str]]     # item_key -> [chunk_id, ...]
    warnings: list[str]
    tokens: TokenUsage
```

**Universal rules for all agents:**
1. Output is **structured JSON only** — no prose, no markdown fences. Validate against a Pydantic schema. On validation failure: retry once with the validation error appended; on second failure, mark the item `FAILED` and surface it in the UI. Never silently drop.
2. Every agent runs **map-reduce over batches**, not one giant prompt. Batch size configurable (default: 20 chunks / 15 requirements per call).
3. Every agent call is logged to `LLMCall` with token counts and cost.
4. Temperature 0.2. `max_tokens` 8000.

### Agent 1 — Requirement Extractor

**Goal:** Convert cited source chunks into atomic, EARS-formatted, ambiguity-scored requirements.

**Retrieval strategy:** Do not RAG-query for requirements — you'd miss coverage. Instead **sweep the entire corpus**: iterate over all chunks grouped by source document, in document order, batched. RAG is used *afterwards* for the enrichment pass (finding corroborating/conflicting evidence across documents).

**EARS patterns (implement all six, reject anything else):**

| Pattern | Template |
|---|---|
| Ubiquitous | `The <system> shall <response>.` |
| Event-driven | `When <trigger>, the <system> shall <response>.` |
| State-driven | `While <state>, the <system> shall <response>.` |
| Optional feature | `Where <feature is included>, the <system> shall <response>.` |
| Unwanted behaviour | `If <unwanted condition>, then the <system> shall <response>.` |
| Complex | Combination of the above (e.g. `While <state>, when <trigger>, the <system> shall <response>.`) |

**Ambiguity scoring rubric** (implement as a deterministic post-processor, NOT as an LLM judgement — LLM scores are not reproducible and clients will challenge them):

```python
AMBIGUITY_RULES = [
  ("VAGUE_TERM",      0.15, r"\b(fast|quick|efficient|user-friendly|robust|appropriate|adequate|"
                            r"sufficient|reasonable|as needed|etc\.?|and/or|minimal|optimal|"
                            r"seamless|intuitive|state-of-the-art|flexible|easy)\b"),
  ("PASSIVE_VOICE",   0.10, r"\b(is|are|was|were|be|been|being)\s+\w+(ed|en)\b(?!\s+by\b)"),
  ("NO_ACTOR",        0.20, "no <system> noun resolved from the CMDB/glossary"),
  ("UNQUANTIFIED",    0.20, "contains a comparative (faster/more/less/better) with no numeric target"),
  ("COMPOUND",        0.15, r"\b(and|or)\b appearing in the <response> clause → not atomic"),
  ("UNTESTABLE",      0.25, "no observable output; verbs like 'support', 'handle', 'manage', "
                            "'process' with no measurable post-condition"),
  ("DANGLING_REF",    0.15, "references a document/system/term not in the corpus or glossary"),
  ("NON_CONFORMANT",  0.30, "does not fit any EARS pattern"),
]
score = min(1.0, sum(weights of fired rules))
```

Each fired rule produces `{code, span, explanation, suggestion}` so the UI can underline the offending span and offer a one-click rewrite.

**Additional passes:**
- **Deduplication:** cluster requirements by embedding cosine > 0.92, merge, union their citations.
- **Conflict detection:** for each requirement, RAG-retrieve semantically similar requirements from *other* source documents; if the LLM judges them contradictory, emit a `CONFLICT` warning linking both REQ-IDs.
- **Decomposition:** BUSINESS-level requirements get child FUNCTIONAL requirements (`parent_req_id`).
- **Glossary:** extract domain terms + system names into a project glossary (used to resolve `<system>` in EARS and to fire `NO_ACTOR` / `DANGLING_REF`).

**Prompt (system):**

```
You are a senior business analyst extracting requirements from enterprise source material.

You will receive numbered source chunks. Extract every distinct requirement that the source
material states or clearly implies. Do not invent requirements. Do not extrapolate industry
best practice. If the source does not support it, it does not exist.

For each requirement:
- Write ONE atomic statement using exactly one EARS pattern (definitions below).
- Use the exact system name from the provided glossary. If no system can be resolved,
  set system_name to null — do NOT guess.
- Cite the chunk id(s) that support it and include the verbatim supporting span from each.
- Classify: level, priority (MoSCoW, only if the source signals it, else SHOULD).
- Write 2–5 acceptance criteria, each independently verifiable.
- If the source is ambiguous, DO NOT resolve the ambiguity yourself — transcribe it faithfully.
  The downstream scorer will flag it and a human will fix it.

EARS PATTERNS:
{ears_reference}

GLOSSARY:
{glossary}

Return JSON matching this schema, and nothing else:
{schema}
```

**Output schema:** `list[ExtractedRequirement]` where each has `title, statement, ears_pattern, ears_parts, level, priority, rationale, acceptance_criteria, citations: [{chunk_id, quoted_span}]`.

**Gate 1:** BA reviews the requirement grid. Bulk-approve, per-item reject with reason, inline-edit (edit sets `created_by_agent=false` and re-runs the ambiguity scorer). Requirements with `ambiguity_score > project.config.ambiguity_threshold` (default 0.4) are **blocked from approval** until edited — surface this hard.

### Agent 2 — BRD Author

**Goal:** Render approved requirements into a client-templated, sectioned BRD.

**Input:** All `APPROVED` requirements + glossary + project metadata + the client's `.dotx` template with its `section_map`.

The agent does **not** write the requirements (they're already fixed). It writes the **connective tissue**: executive summary, scope/out-of-scope, business context, process narratives, assumptions, dependencies, risks — and it slots the requirement tables into the right sections.

**Section map** (`Template.section_map`) drives everything:

```json
{
  "sections": [
    {"key": "exec_summary",   "heading": "1. Executive Summary",        "mode": "GENERATED", "max_words": 400},
    {"key": "background",     "heading": "2. Business Context",         "mode": "GENERATED", "max_words": 800},
    {"key": "scope",          "heading": "3. Scope",                    "mode": "GENERATED"},
    {"key": "as_is",          "heading": "4. AS-IS Process",            "mode": "GENERATED", "source_filter": {"doc_class": ["PROCESS_MAP","AS_IS_DOC"]}},
    {"key": "br",             "heading": "5. Business Requirements",    "mode": "REQ_TABLE",  "filter": {"level": "BUSINESS"}},
    {"key": "fr",             "heading": "6. Functional Requirements",  "mode": "REQ_TABLE",  "filter": {"level": "FUNCTIONAL"}},
    {"key": "nfr",            "heading": "7. Non-Functional Requirements","mode": "REQ_TABLE","filter": {"level": "NON_FUNCTIONAL"}},
    {"key": "assumptions",    "heading": "8. Assumptions & Dependencies","mode": "REQ_TABLE", "filter": {"level": ["ASSUMPTION","CONSTRAINT"]}},
    {"key": "glossary",       "heading": "9. Glossary",                 "mode": "GLOSSARY"},
    {"key": "traceability",   "heading": "10. Traceability Summary",    "mode": "RTM_SUMMARY"}
  ]
}
```

`mode`:
- `GENERATED` → LLM writes prose, RAG-grounded, citations rendered as footnotes.
- `REQ_TABLE` → deterministic python-docx table render (no LLM). Columns: REQ-ID | Statement | Priority | Acceptance Criteria | Source.
- `GLOSSARY` / `RTM_SUMMARY` → deterministic.

**python-docx implementation notes:**
- Open the client `.dotx`, **do not build styles from scratch**. Read the template's existing named styles (`Heading 1`, `Table Grid` or client equivalents) and reference them by name. If a required style is missing, fail loudly at template-registration time, not at render time.
- Insert content by locating heading placeholders (`{{SECTION:exec_summary}}`) in the template body and replacing the paragraph in-place at the XML level (`paragraph._element.getparent()`), preserving surrounding formatting.
- Populate document properties (title, author, subject) and any content controls / docvariables the template exposes.
- Regenerate the TOC field so page numbers resolve on first open (`w:fldSimple` with `TOC \o "1-3" \h \z \u` + set `updateFields` in settings.xml).

**Gate 2:** Architect/BA reviews the BRD. UI shows a section-by-section diff against the previous version, with an inline comment thread per section. Rejecting a section re-runs only that section.

### Agent 3 — Test Designer

**Goal:** For each APPROVED requirement, generate a test case set that satisfies the project's coverage policy.

**Coverage policy** (`project.config.coverage_policy`, enforced deterministically before the gate opens):

```json
{
  "min_per_requirement": {
    "POSITIVE": 1,
    "NEGATIVE": 1,
    "EDGE": 0
  },
  "acceptance_criteria_coverage": "EVERY_AC_MAPPED",   // each AC must appear in ≥1 TC's expected results
  "nfr_policy": "PERFORMANCE_OR_EXPLICIT_WAIVER",
  "boundary_required_when": "requirement contains a numeric range or limit"
}
```

If the generated set fails the policy, the orchestrator **automatically re-prompts the agent with the specific gap** ("REQ-0042 has no NEGATIVE test; its AC #3 is unmapped") before surfacing to the human. Do not present a non-compliant set to a reviewer.

**Prompt (system):**

```
You are a senior test architect. For the requirement below, design test cases.

REQUIREMENT {req_id} [{ears_pattern}]:
{statement}

ACCEPTANCE CRITERIA:
{acceptance_criteria}

SOURCE CONTEXT (for realistic test data — use actual field names, codes, and values found here):
{cited_chunks}

INCIDENT EVIDENCE (real failures observed in production for this application — design NEGATIVE
and EDGE cases that would have caught these):
{related_incident_clusters}

Rules:
- Every test case maps to exactly one requirement and cites which acceptance criteria it verifies.
- Steps must be concrete and executable by a person who has never seen the system:
  bad  -> "Verify order is processed correctly"
  good -> "Click [Submit Order]. Expected: order status changes to 'Confirmed' and an
           order number in format ORD-NNNNNNNN is displayed in the confirmation banner."
- Use real field names and codes from the source context. Never use placeholder data
  like 'test123' or 'John Doe' if the source gives you actual formats.
- Derive at least one NEGATIVE case from the EARS 'unwanted behaviour' clause if present,
  or from the incident evidence.
- Assign test_level based on where the requirement is verifiable, not by default.

Return JSON matching {schema}, nothing else.
```

**The incident-evidence injection is the differentiator.** Negative test cases derived from 12 months of real production incidents are the thing that makes a client say "no other vendor did that."

**Gate 3:** Test Lead reviews. Grid grouped by requirement, with a live **coverage heatmap** in the header (requirements with gaps highlighted red). Bulk approve / per-item edit.

### Agent 4 — Script Generator

**Goal:** Convert APPROVED test cases into executable artifacts. Pluggable emitters.

```python
class ScriptEmitter(Protocol):
    target: str
    def can_handle(self, tc: TestCase) -> bool: ...
    def generate(self, tc: TestCase, ctx: ProjectContext) -> TestScript: ...
    def validate(self, script: TestScript) -> ValidationResult: ...
```

Implement four emitters:

| Emitter | Applies to | Output | Validation |
|---|---|---|---|
| **PlaywrightEmitter** | `test_level ∈ {UI_E2E}` | TypeScript `.spec.ts` + Page Object Model classes. Use `getByRole`/`getByLabel` locators — **never CSS/XPath**. `test.step()` per TC step so the report maps 1:1 to the test case. Tag with `@REQ-0042 @TC-0113`. | `tsc --noEmit` + `eslint` (see §4a sandbox) |
| **PytestEmitter** | `test_level ∈ {API, INTEGRATION, UNIT}` | pytest + `httpx`, parametrized fixtures, `pytest.mark.requirement("REQ-0042")` | `python -m py_compile` + `pytest --collect-only` |
| **KarateEmitter** | `test_level ∈ {API}` | `.feature` files, Karate DSL, scenario outlines from test data tables | Gherkin AST parse |
| **ToscaEmitter** | any | Tosca-importable XML (`<TCObject>` / `<TestCase>` with `<TestStepValue>` nodes) + `TestCase-Design` sheet as XLSX for Tosca's Test Case Design import | XSD validation |

#### §4a — Static validation sandbox (no containers available)

Validation compiles/parses **untrusted, LLM-generated code**. With Docker off the table, isolate it with Windows-native primitives — do **not** just `subprocess.run()` it as the service account.

1. Provision a **dedicated low-privilege local user** `svc_tfsandbox` (member of nothing; deny "Log on locally"; no rights to the app directory, the DB, or Key Vault).
2. Each validation runs in a **fresh scratch directory** under `D:\sandbox\{run_id}\{ts_id}`, ACL'd so only `svc_tfsandbox` can read/write it. Deleted on completion.
3. Launch the toolchain (`tsc`, `eslint`, `python -m py_compile`, `pytest --collect-only`, Karate's Gherkin parser, `xmllint` for Tosca XSD) via `CreateProcessAsUser` inside a **Windows Job Object** with:
   - `JOB_OBJECT_LIMIT_ACTIVE_PROCESS = 8`
   - `JOB_OBJECT_LIMIT_JOB_MEMORY = 1 GB`
   - `JOB_OBJECT_LIMIT_JOB_TIME = 60 s`
   - `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
   (use `pywin32` / `win32job`, or shell out to a small C# helper — either is fine)
4. **Block network egress from the sandbox user** with a Windows Firewall outbound rule scoped to `svc_tfsandbox`. Generated code must never be able to phone home.
5. `npm install` is **never** run at validation time. Pre-install `typescript`, `eslint`, `@playwright/test` once, at deploy time, into `D:\toolchain\node_modules`, and point the sandbox at it with `NODE_PATH`. Node.js LTS is a VM prerequisite.
6. **Never execute the tests** — only type-check, lint, and collect. `pytest --collect-only` imports modules, so keep the sandbox constraints on even for that.

**Emitter must NOT hallucinate selectors.** If the project has no UI artefacts (no DOM snapshot, no Figma, no screenshots), generate the Playwright script with **explicit `TODO_LOCATOR('Submit Order button')` markers** and set `compiles=false`, `status=DRAFT` with a warning. Fabricated `#submit-btn` selectors are worse than useless — they create the illusion of a working suite. Make this policy visible in the UI.

Optional (Phase 3): allow the user to upload a DOM snapshot / HAR / Storybook URL per project; the emitter then resolves real locators and clears the TODO markers.

**Every generated script carries a traceability header:**

```typescript
/**
 * @generated-by TraceForge
 * @requirement REQ-0042 — "When a customer submits an order exceeding their credit limit,
 *                          the Order Management System shall reject the order and display
 *                          error code ORD-CR-001."
 * @test-case  TC-0113 (NEGATIVE) — Order rejection on credit limit breach
 * @source     SOW_v3.docx p.12 §3.2; INCIDENT PATTERN: credit-check-timeout (n=347)
 * @generated  2026-07-11T09:14:22Z
 * DO NOT EDIT the traceability header. Edits below are preserved on regeneration.
 */
```

**Gate 4:** Reviewer sees Monaco side-by-side: test case (left) / generated script (right), with compile status. Human edits are preserved on regeneration via a protected-region marker (`// <traceforge:custom>` … `// </traceforge:custom>`).

## 6. Orchestration & Human-in-the-Loop

### 6.1 State machine

```
INGEST ──► EXTRACT ──[GATE 1: BA]──► BRD ──[GATE 2: Architect]──► TEST_DESIGN
   ──[GATE 3: Test Lead]──► SCRIPT_GEN ──[GATE 4: Reviewer]──► RENDER ──► DONE
```

Rules:
- A stage transitions to `AWAITING_APPROVAL` on completion and **blocks**. The orchestrator does not proceed.
- Gates support **partial approval**: approve 47 of 52 requirements, reject 5 with comments. Rejected items go back to the agent for a targeted re-run (scope = the rejected IDs only), and the gate reopens for just those.
- `APPROVED_WITH_COMMENTS` proceeds but records the comments in the audit trail.
- Gate configuration is per-project: a gate can be marked `auto_approve: true` for internal demos, but this must be **loudly visible in the UI and stamped on every generated artifact** ("⚠ Generated with auto-approval — not reviewed by a human"). Do not let this become invisible.

### 6.2 Suspect-link propagation (P4)

When an APPROVED `Requirement`'s `content_hash` changes:

```
1. requirement.status → APPROVED (new version), previous version → SUPERSEDED
2. All TestCases where upstream_req_hash != requirement.content_hash → status = SUSPECT
3. All TestScripts whose parent TC is SUSPECT → status = SUSPECT
4. BRD sections containing this REQ → flagged STALE
5. Create a delta PipelineRun scoped to the suspect items only
6. UI: a persistent banner — "3 requirements changed → 11 test cases and 11 scripts are suspect.
   [Review impact] [Regenerate affected]"
```

**Never auto-regenerate without a human clicking.** Never delete a suspect item — a human may have hand-edited it.

### 6.3 Cost & guardrails
- Per-project token budget with a hard stop and a UI warning at 80%.
- `LLMCall` metering surfaced in the run detail view: tokens, cost, latency, retry count per agent.
- Rate limiting + exponential backoff on 429s.
- All prompts and completions optionally persisted (config flag `PERSIST_LLM_IO`) for audit; **redact PII before persisting** (run a Presidio pass on ingestion and store an entity map, not raw values, for anything classified as PII).

## 10. Delivery Phases & Acceptance Criteria

### Phase 0 — Platform (do this before writing a line of application code)
- `Bootstrap-VM.ps1` + `Configure-IIS.ps1` run clean on a fresh Windows Server 2022 VM.
- A hello-world FastAPI app answers on `https://<vm>/api/v1/health` **through IIS**, not through a raw uvicorn port.
- The SSE endpoint streams (not buffers) through IIS. **Acceptance: `curl -N https://<vm>/api/v1/health/sse-test` emits one event per second, live.** If events arrive in a single burst at the end, `web.config` is wrong — fix it now, because every progress bar in the product depends on it.
- Arq worker runs as a Windows Service, survives an `iisreset`, and picks up a queued job.
- Azure Database for PostgreSQL Flexible Server reachable with `CREATE EXTENSION vector;` succeeding.
- **Do not proceed until all five pass.** Every one of these has bitten a Python-on-IIS deployment.

### Phase 1 — Spine
- Postgres+pgvector migrated; Entra ID auth working end-to-end.
- Upload a `.docx` → parse → chunk → index → chunks visible in the UI with correct locators.
- Agent 1 extracts requirements with citations. **Acceptance: 100% of generated requirements have ≥1 citation with a resolvable locator, verified by an automated test. Zero exceptions.**
- Requirements Workbench renders, citation drawer resolves back to highlighted source text.
- Gate 1 blocks the pipeline. **Acceptance: attempting to start Agent 2 via the API while Gate 1 is PENDING returns 409.**

### Phase 2 — Full chain
- Agents 2–5. BRD renders into the client `.dotx` with correct styles and a working TOC.
- Test Designer + coverage policy enforcement (auto re-prompt on gap).
- Playwright + pytest emitters with real static validation in a sandbox container.
- RTM XLSX with fully formula-driven Coverage Summary. **Acceptance: opening the RTM and deleting a row causes all coverage percentages to recalculate correctly — no hardcoded derived values anywhere in the workbook.**
- Evidence pack ZIP with MANIFEST.

### Phase 3 — ServiceNow + change management
- ServiceNow connector with incident clustering + synthesized pattern chunks + INC drill-down.
- Incident-evidence injection into the Test Designer.
- Suspect-link propagation + delta re-runs. **Acceptance: edit an approved requirement → exactly the affected TCs and TSs become SUSPECT, nothing is deleted, the impact banner reports the correct counts.**
- Karate + Tosca emitters.

### Phase 4 — Enterprise hardening
- RBAC, Entra ID groups → roles, PII redaction, air-gapped LLM profile (self-hosted vLLM/Ollama on a GPU VM in the same VNet) proven end-to-end.
- Cost budgets, prompt versioning, full audit export.
- Load test: 500-page corpus → 800 requirements → 2,400 test cases without timeout. **Acceptance: an app-pool recycle mid-run does not lose the run** — the work is in the worker service, the API is stateless, and the run resumes from its persisted state.
- Blue/green or slot-style deploy: Web Deploy to a staging physical path, then swap the IIS site's physical path — no long downtime.

## 12. Explicit Non-Goals

Do not build: a chat interface, a test *execution* engine (we generate scripts, we don't run the suites — hand off to the client's CI), a defect manager, a project-management module. Every hour spent on these is an hour not spent on the traceability spine, which is the only thing that differentiates this from a prompt in a text box.
